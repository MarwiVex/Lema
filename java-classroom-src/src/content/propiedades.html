16. Archivos de Propiedades (.properties) y Locale

Nunca debes escribir contraseñas, URLs de servidores o parámetros de configuración directamente quemados (hardcoded) dentro de tus clases Java. Si la dirección de la base de datos cambia en producción, tendrías que recompilar todo el proyecto. Para resolver esto, Java incluye la clase java.util.Properties y el manejo de configuración regional con java.util.Locale.

1. Estructura de un Archivo .properties

Un archivo .properties es un fichero de texto plano donde cada línea almacena un par clave=valor. Las líneas que comienzan con almohadilla (#) son comentarios ignorados por Java. En el proyecto BaseDatos se utilizan dos archivos clave:

config.properties (En la raíz del proyecto) 
#pues chad no?
#Sun Nov 08 21:20:36 CST 2026
app.debug=true
app.nombre=Skibidi app
app.version=67.67.1
src/main/resources/database.properties 
# Configuracion de conexion a la base de datos MySQL (Servidor)
db.url=jdbc:mysql://localhost:3306/informacion_db
db.user=root
db.password=

# Configuracion de conexion local de respaldo (SQLite)
db.local.url=jdbc:sqlite:informacion.db

2. Crear y Guardar un Archivo .properties desde Java

Con setProperty(clave, valor) defines las claves en memoria y con store(FileOutputStream, comentario) generas automáticamente el archivo físico en disco incluyendo la fecha y el comentario de cabecera:

CrearPropiedad.java (Proyecto BaseDatos) 
package com.example.basedatos.Propiedades;

import java.io.FileOutputStream;
import java.util.Properties;

public class CrearPropiedad {
    public static void main(String[] args) {
        Properties propiedad = new Properties();
        
        // Asignamos pares clave -> valor (siempre como Strings)
        propiedad.setProperty("app.nombre", "Skibidi app");
        propiedad.setProperty("app.version", "67.67.1");
        propiedad.setProperty("app.debug", "true");

        // try-with-resources cierra el FileOutputStream automáticamente
        try (FileOutputStream fos = new FileOutputStream("config.properties")) {
            propiedad.store(fos, "pues chad no?");
            System.out.println("Archivo config.properties generado con éxito.");
        } catch (Exception e) {
            throw new RuntimeException(e);
        }
    }
}

3. Cargar Propiedades: Disco vs Classpath (resources)

Existen dos maneras de leer un archivo .properties dependiendo de dónde esté ubicado:

A. Con FileInputStream (Raíz del proyecto)

Ideal cuando el archivo config.properties está fuera del JAR (en la carpeta de trabajo del usuario) y quieres que pueda modificarse y guardarse en tiempo de ejecución.

B. Con getResourceAsStream (Carpeta resources)

Ideal cuando el archivo (como /database.properties) vive dentro de src/main/resources y viaja empaquetado dentro del ejecutable o classpath de Maven.

CargarPropiedades.java (Lectura y parseo de tipos) 
package com.example.basedatos.Propiedades;

import java.io.FileInputStream;
import java.util.Properties;

public class CargarPropiedades {
    public static void main(String[] args) {
        String nombre = "";
        String version = "";
        Boolean debug = true;
        Properties propiedad = new Properties();

        try (FileInputStream fis = new FileInputStream("config.properties")) {
            propiedad.load(fis);
            nombre = propiedad.getProperty("app.nombre");
            version = propiedad.getProperty("app.version");
            // Como getProperty devuelve String, convertimos a boolean con Boolean.parseBoolean
            debug = Boolean.parseBoolean(propiedad.getProperty("app.debug"));
        } catch (Exception e) {
            System.err.println(e.getMessage());
        }

        System.out.printf("%s %s %b%n", nombre, version, debug);
    }
}

Uso de Valores por Defecto (Fallback) en getProperty

El método sobrecargado propiedades.getProperty("clave", "valorPorDefecto") devuelve el segundo argumento si la clave no existe en el archivo. En Datos.java se encadena para soportar distintos nombres de clave o un valor de respaldo seguro:

String urlServer = propiedades.getProperty("db.url", propiedades.getProperty("url", "jdbc:mysql://localhost:3306/informacion_db"));
String user = propiedades.getProperty("db.user", "root");
String urlLocal = propiedades.getProperty("db.local.url", "jdbc:sqlite:informacion.db");

4. java.util.Locale y el Peligro de %f en Consultas SQL

La clase Locale define la convención regional e idioma de la JVM (formato de fechas, monedas y separador decimal). Observa el experimento del archivo EjemploLocales.java del repositorio BaseDatos:

EjemploLocales.java (Proyecto BaseDatos) 
package com.example.basedatos.Locales;

import java.util.Locale;

public class EjemploLocales {
    public static void main(String[] args) {
        float valor = 1.5f;

        // En España (es_ES) y varios países hispanohablantes, el separador decimal es la COMA (,)
        Locale.setDefault(new Locale("es", "ES"));
        System.out.println("Con Locale es_ES: " + String.format("%f", valor)); // Imprime: 1,500000

        // En EE.UU. (en_US) y México (es_MX), el separador decimal es el PUNTO (.)
        Locale.setDefault(Locale.US);
        System.out.println("Con Locale US:    " + String.format("%f", valor)); // Imprime: 1.500000
    }
}

¿Por qué Locale puede romper tus INSERT o UPDATE en SQL?

En AdmonCafe.java, la consulta SQL se construye con String.format:

String consulta = String.format("INSERT INTO Cafe(Productor, VariedadCafe, Cantidad) VALUES('%s', %d, %f)", productor, variedad, cantidad);

Si la PC donde corre el programa tiene Locale("es", "ES"), entonces %f convierte 2.5f en 2,500000 (con coma). La consulta resultante será:
INSERT INTO Cafe(Productor, VariedadCafe, Cantidad) VALUES('FincaSol', 1, 2,500000)
¡SQL interpretará la coma de 2,500000 como un cuarto valor separado y lanzará un SQLException: column count doesn't match value count!

Soluciones: Pasar explícitamente String.format(Locale.US, "INSERT ...", ...), configurar Locale.setDefault(Locale.US) al inicio del programa, o utilizar parámetros ? con PreparedStatement.setFloat().
